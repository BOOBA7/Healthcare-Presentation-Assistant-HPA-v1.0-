# Slice 02.2 — Dashboard evidence

Date: 2026-09-15. Scope: FR-02 and the dashboard-facing parts of NFR-02.
Only 02.2 was authorised. No 02.3 autosave or broader recovery implementation
was started.

## Implementation

- **DASH-01:** Added the owner-scoped `GET /users/{user_id}/dashboard` route.
  It returns persisted, metadata-only cards without loading a model provider.
- **DASH-02:** Each card contains the Project name, workflow status, presentation
  context (topic, audience, duration, target slide count, objectives and special
  instructions), chosen built-in theme or custom-template filename, associated
  resource count/types, up to five recent audit actions, and the last successful
  state-save timestamp.
- **DASH-03:** `last_successful_save` is the SQLite `project_sessions.updated_at`
  value. State, timestamp and audit event are written in the existing transaction.
  A failed or stale write rolls back, so it cannot create a dashboard success.
- **DASH-04:** `/app` fetches this dashboard at startup and after successful
  material actions. It displays responsive FR/EN cards and an explicit Resume
  button. Resume selects the saved Project, retains the existing per-Project
  workspace choice and loads its normal, server-owned Project response.
- **DASH-05:** Versioned web asset URLs are updated with the dashboard release,
  so a browser cannot retain the previous JavaScript/CSS bundle after reload.
- **DASH-06:** The dashboard does not expose source text, raw PDF pages, model
  prompts, tokens, private scope explanations, or unrelated users' records.
  The existing project selector remains available as a secondary resume path.

The implementation preserves SQLite revision checks, atomic `save_with_event`,
local account ownership, prototype policy, deterministic workflow guards and
the phase 02.1 context-attestation gate. No dashboard write, workflow transition,
style-selection behaviour, resource lifecycle, export logic, Streamlit feature,
or external provider call was introduced.

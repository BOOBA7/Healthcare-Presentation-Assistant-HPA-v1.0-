## Concrete outcome

- An additive `owner_resources` table retains the professor's source independently
  of Project attachments. Existing normalized resources and embedded legacy
  snapshots are copied into this library on startup without fabricating originals,
  dates or approvals. Existing Project resource/page/chunk tables remain in use.
- Removing a resource from a Project keeps its library original. The owner can
  explicitly add it to another Project, subject to existing screening/date gates.
  Presentation selection remains a separate explicit operation.
- Permanent deletion removes the owner's library record and every attachment,
  original BLOB, page and retrieval chunk for that source ID across Projects.
  It clears dependent generated material, approval flags, execution results,
  transcripts, memory summaries and generation records in affected Projects.
  Human context, account information and other owners' resources are preserved.
- Affected jobs become cancelled and lose stored results/errors. Late progress
  and results cannot overwrite cancelled jobs. Stale Project writes fail revision
  checks; durable source/Project deletion markers prevent recreation under deleted
  IDs after restart. Reimporting deliberately requires a new source ID.
- Old audit event identities, types, actors and timestamps remain, while payloads
  that could contain source quotations are redacted. Deletion records retain
  only actor, source ID and timestamp. Project deletion keeps the owner library;
  account deletion removes it.
- `/app` exposes personal-library membership, Add to Project, Remove from Project
  and Delete permanently in French and English, with different confirmations.
  Owner-scoped API routes enforce the same separation. Cancelled jobs produce
  an explicit reload message instead of being shown as successful jobs.

## Decisions and guarantees

### Transactions and integrity

Source deletion, dependency invalidation, revision changes, cancellation, audit
and tombstones commit together under `BEGIN IMMEDIATE`. The owner-library writer
also independently screens and verifies originals, so calling that helper directly
cannot bypass checks. Missing-original insertion requires matching already
persisted historical content owned by the same user. All repository source
entry points retain screening and original verification. Direct `_sync_resources`
removal requires the state transaction's private capability so it cannot silently
remove cache rows while keeping a stale Project snapshot. Owner-ID collisions
with different originals fail before writing the batch. Same resource IDs remain
independent across different owners.

Historical source metadata migration and its unknown fields remain unchanged.
The new owner-library startup migration is an additive durable migration, so an
old test's snapshot boundary now follows constructor migration and still proves
that ordinary reads do not write. Existing canonical records are not overwritten
by conflicting Project copies on subsequent restarts; corrupted copies remain
readable for recovery and fail the existing integrity gates on scientific use.
An initial migration containing conflicting originals under the same owner/source
ID fails closed and requires resolving the identity collision; it never silently
chooses or deletes one original.

### Internal exports and recovery

New web/API PowerPoint exports render to `BytesIO`, pass existing export gates,
and commit the export event/state before returning bytes with `no-store`. A
failed or stale save returns no deck and leaves no internal export file.
The explicit file-output domain use case remains available for existing callers;
files deliberately exported elsewhere belong to the professor.

Legacy application exports use `<presentation UUID>-<8 hex digits>.pptx` in the
internal `exports` directory. Cleanup records accepted audited names and matching
interrupted-export files before changing source state. The original root is
stored in SQLite, so a later process working directory cannot redirect cleanup.
Only these application filenames are eligible. Unlinking a file symlink leaves
its target untouched; a symlink replacing the exports root causes pending cleanup.
A legacy presentation ID shared across owners is refused as ambiguous rather
than deleting another owner's files. Arbitrarily renamed/unregistered files or
external output directories cannot be attributed safely and are not traversed.

`secure_delete=ON` clears deleted SQLite cells; a WAL truncate checkpoint follows
commit. File failures or a busy checkpoint leave durable pending cleanup, retried
on restart and subsequent material saves. Source/Project deletion routes return
202 with `cleanup_pending` where applicable; the source is already unavailable.
Deletion is idempotent. Pending cleanup is not reported as completed.

These mechanisms remove application-managed durable copies. They do not promise
forensic erasure from SSD snapshots/backups, revoke already downloaded copies,
or retract an already running external provider request. Cancelled/stale work
cannot persist its result through the guarded repository paths. Direct arbitrary
SQL edits by someone controlling the filesystem are outside these guards.

### Supported scope

Phase 03 still accepts the conservative text-PDF subset from 03.1. No extracted
image/table byte store exists yet; deleting the source also deletes its descriptor
metadata. OCR, additional formats/assets, professional data and phase 04 work
were not added. Date evidence remains bounded to the documented 03.2 parser.
No scientific, anonymisation, regulatory or full PRD compliance is claimed.
